# Velocity Template Language for Zed

[Velocity Template Language](https://velocity.apache.org/engine/2.3/user-guide.html)
(VTL) support for the [Zed](https://zed.dev) editor, powered by a dedicated
[tree-sitter grammar](https://github.com/Aladushek04/tree-sitter-vtl).

## Features

- Syntax highlighting for references (`$foo`, `$!foo`, `${foo}`, `$foo.bar()`,
  `$foo[0]`), directives (`#if`, `#foreach`, `#set`, `#macro`, `#parse`,
  `#include`, `#define`, `#evaluate`, `#stop`, `#break`, `#@macro()` calls),
  comments (`##`, `#* ... *#`, `#** ... *#`), literal blocks (`#[[ ... ]]#`)
  and expressions (strings, numbers, booleans, lists, maps, ranges, operators).
- Bracket matching for `()`, `[]`, `{}`.
- Auto-indentation for `#if`/`#elseif`/`#else`, `#foreach`, `#macro`,
  `#define` and `#@macro` calls.
- Outline panel entries for `#macro` and `#define` blocks.
- `##` comment toggling.
- HTML/XML markup and JSON payloads around Velocity constructs are highlighted
  through language injections. This uses Zed's built-in HTML and JSON grammars,
  so nothing extra has to be installed.
- Map keys in references (`$map['key']`) are highlighted as properties rather
  than as strings.

File extensions: `.vtl`, `.vm`, `.velocity`.

## Install (local development)

The grammar version referenced by `extension.toml` must be a Git commit. Zed
clones it from [tree-sitter-vtl](https://github.com/Aladushek04/tree-sitter-vtl)
when building the extension, so nothing has to be fetched manually. To work on
the grammar locally, clone it next to this directory and re-pin the manifest to
your checkout:

```sh
git clone https://github.com/Aladushek04/tree-sitter-vtl tree-sitter-vtl
./scripts/setup-grammar.sh                     # local file:// checkout
./scripts/setup-grammar.sh https://github.com/Aladushek04/tree-sitter-vtl
```

The first form is meant for local development, the second points the manifest
back at the published grammar (both also pin the current grammar commit).

Then in Zed:

1. Open the command palette.
2. Run `zed: install dev extension`.
3. Select this directory (the one containing `extension.toml`).

Open any `.vm` or `.vtl` file to see the language in action. There is a sample
template in `examples/example.vm`.

## Checking templates

`./scripts/check-templates.sh` parses every template in `examples/` and fails
if the grammar produces `ERROR` or `MISSING` nodes, which is handy after
changing the grammar:

```sh
./scripts/check-templates.sh
```

The script uses the tree-sitter CLI from `tree-sitter-vtl/node_modules` (see
"Grammar development") or a globally installed `tree-sitter`.

## Publishing the grammar and the extension

Zed downloads grammars from a Git repository, so the grammar lives in its own
repository: <https://github.com/Aladushek04/tree-sitter-vtl>. The manifest pins
a grammar commit, so after changing the grammar:

1. Push the grammar change to `tree-sitter-vtl`.
2. Re-pin the manifest to the new commit:

   ```sh
   ./scripts/setup-grammar.sh https://github.com/Aladushek04/tree-sitter-vtl
   ```

3. Push the extension. To publish it, add
   [`zed-velocity`](https://github.com/Aladushek04/zed-velocity) to
   [zed-extensions](https://github.com/zed-industries/extensions).

## Repository layout

```
extension.toml               Zed extension manifest
languages/vtl/               language config, queries and injections
tree-sitter-vtl/             standalone tree-sitter grammar (own Git repository,
                             cloned separately, not tracked here)
examples/example.vm          sample booking template (all VTL constructs)
scripts/setup-grammar.sh     pins the grammar repository/revision
scripts/check-templates.sh   reports grammar errors in examples/
```

## Grammar development

```sh
cd tree-sitter-vtl
npm install          # provides the tree-sitter CLI
npm run generate
npm test             # corpus tests
npm run parse -- examples/example.vm
```

The generated parser is committed (`tree-sitter-vtl/src/parser.c`), so Zed does
not need the tree-sitter CLI to build the extension.

## Known limitations

- VTL has no official language server, so there is no completion, go-to
  definition or diagnostics; support is limited to tree-sitter features.
- Markup generated by a template (HTML, XML, JSON, ...) is highlighted as plain
  text, because VTL files are used for many output formats.
- Markup highlighting is fragment-based: directives and references split a
  template into many `text` nodes, each parsed on its own, so some tags or JSON
  fragments may stay unstyled. This never affects VTL highlighting.
- A `#` followed by a letter is always treated as a directive or macro call
  (`#fff` in CSS included), which matches how Velocity itself tokenizes input.
